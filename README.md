### Что делает предлагаемый prepare-commit-msg хук

Хук `prepare-commit-msg` вызывается после подготовки файла с дефолтным сообщением коммита, но до открытия редактора для его редактирования. Хук позволяет автоматически изменять подготовленное сообщение или дополнять его информацией, например `scope` и идентификатором задачи.

Предлагаемый `prepare-commit-msg`:
1. Добавляет в сообщение `scope`, указывающий на часть репозитория, в которой были сделаны изменения.
2. Добавляет в конец сообщения идентификатор задачи из вашей системы управления проектами (часто Jira).

### Зачем формировать scope?
`scope` помогает быстро определить по истории `git log`:
1. В каком логическом модуле были сделаны изменения.
2. Какая команда отвечает за эти изменения.

В одном репозитории могут работать несколько команд, например команда разработки и команда автоматизации тестирования. Чтобы быстро различать их коммиты и понимать, какие модули затронуты изменениями, предлагается включать в `scope` лейбл команды и название модуля.

### Зачем добавлять идентификатор задачи?
Чтобы понимать, глядя на `git log`, в рамках какой задачи изменялся код. Такая подсказка позволит быстрее восстановить контекст, заглянув в систему управления проектами.

### Пример commit-сообщения после работы prepare-commit-msg
```
(dev module1): summary commit-сообщения

Основное тело commit-сообщения.

PROJ-12345
```

### Как мы формируем scope?
`scope` формируется в хуке при помощи функции `make_general_scope`.
Мы выделяем сгенерированный `scope` от `summary` с помощью круглых скобок и двоеточия: `(scope): summary`.
Часто `scope` состоит из лейбла команды и лейбла модуля, определяемого на основании общего пути изменённых файлов.
Если изменения затрагивают несколько частей репозитория, `scope` может содержать несколько подскоупов, разделённых запятыми.
В большинстве случаев `scope` выглядит вот так `(dev module1):`, другие возможные варианты будут описаны ниже в _примерах_.

Чтобы автоматически формировать `scope` с учётом структуры репозитория и распределения ответственности между командами, необходимо задать правила, по которым будут определяться соответствующие лейблы.
Для этого в файле `githooks_config.sh` нужно определить ассоциативный массив для каждой команды. Рассмотрим пример.
Предположим, что команда тестирования работает в директории `code/tests`, а команда разработки — в родительской директории `code`.

```bash
declare -A team1_rules=(
    ['code/tests']="qa"
    ['code/tests/Module1']="mod1"
    ['code/tests/Module2']="mod2"
)

declare -A team2_rules=(
    ['code']="dev"
    ['code/Module1']="mod1"
    ['code/Module2']="mod2"
)
```

В данных массивах _ключ_ — это путь относительно корня репозитория, _значение_ — это лейбл, который будет помещаться в `scope`, если в рамках коммита будут изменены файлы из директории, указанной в ключе.
Каждый массив правил должен содержать правило для базовой директории (`code`, `code/tests`), остальные правила описывают её поддиректории.

**ВАЖНО!** Если несколько групп правил могут одновременно применяться к одним и тем же файлам, порядок передачи правил в функцию `make_general_scope` влияет на результат, поэтому правила для более специфичных директорий следует передавать в функцию раньше правил для более общих директорий.
В примере выше как раз такая ситуация: `code/tests` является поддиректорией для `code`, поэтому для корректной работы хука функция получает аргументы в определенном порядке: `make_general_scope <other args> team1_rules team2_rules`.
Если директории, для которых заданы правила, располагаются на одном уровне, например `./code` и `./tests`, то порядок передачи аргументов в функцию не важен.

#### Примеры
- Если в индекс Git попал файл `code/tests/Module1/tests.cs`, то при коммите `scope` будет выглядеть `(qa mod1):`.
- Если в индекс попал файл `code/Module1/code.cs`, то `scope` будет выглядеть `(dev mod1):`.
- Если в индекс попали файлы `code/Module2/code21.cs` и `code/Module2/code22.cs`, то `scope` будет выглядеть как `(dev mod2):`, так как общий путь для файлов в этом случае `code/Module2`, что соответствует лейблу `mod2`.
- Если в индекс попали файлы `code/Module1/code1.cs` и `code/Module2/code2.cs`, то `scope` выглядит как `(dev):`, то есть будет вычислен общий путь для двух измененных файлов — это просто `code`, и уже на основании этого результата будет добавляться подходящий лейбл, в этом примере - это `dev`.
- Если в индекс попали файлы `code/Module1/code.cs`, `code/tests/README.md`, `code/tests/Module1/test.cs`, то `scope` окажется `(dev mod1, qa):`, то есть в случае, когда изменения попадают под обе группы правил, мы получаем два подскоупа, разделенных запятой. При формировании подскоупа общий путь вычисляется отдельно для файлов, относящихся к его группе правил, поэтому для `code/tests/README.md`, `code/tests/Module1/test.cs` общий путь файлов — это `code/tests`, что соответствует базовой директории с лейблом `qa`.
- Если проиндексированы еще и файлы, которые находятся за пределами указанных вами правил, то при коммите к `scope` добавляется подскоуп `etc` (от лат. _et cetera_ — «и другие»), то есть при измененных `code/Module1/code.cs` и `deploy/configs/complex.cfg`, `scope` окажется `(dev mod1, etc):`.
- Если измененный файл находится внутри базовой директории команды, но для его поддиректории не задан отдельный лейбл, в `scope` включается имя поддиректории. Глубина отображаемого пути регулируется переменной `path_depth` в `githooks_config.sh`. Значение `1` позволяет показывать только ближайшую поддиректорию, не перегружая `scope` деталями.
Для измененного файла `code/ModuleX/SubModule/SubSubModule/code.cs` `scope` будет `(dev ModuleX):`.
- Если проиндексированы файлы из директории, которая не находится под правилами, то в `scope` записывается имя этой директории. Например, в случае измененных `deploy/configs/complex.cfg`, `deploy/configs/some.cfg` получаем `(deploy):`. `path_depth` регулирует глубину отображения и для таких случаев.

#### Замечания
- Ключи могут содержать Windows-пути:
```bash
declare -A team2_rules=(
    ['code']="dev"
    ['code\Module1']="mod1"
    ['code\Module2']="mod2"
)
```
- **ВАЖНО!** Все ключи ассоциативных массивов необходимо заключать в одинарные кавычки. Это единое правило для всех путей, которое позволяет избежать проблем с обработкой специальных символов в Bash, в частности обратных слешей в Windows-путях.

#### Если в репозитории работает больше двух команд
Если в репозитории работают более двух команд или одна команда отвечает за несколько директорий, потребуется добавить соответствующие группы правил в `githooks_config.sh`. Затем нужно скорректировать вызов `make_general_scope` в хуке `prepare-commit-msg`, передав все необходимые группы правил.

1. Добавляем в `githooks_config.sh` третью группу правил и при необходимости корректируем имена остальных массивов.
```bash
declare -A team1_rules=(
    ['code/tests']="qa"
    ['code/tests/Module1']="mod1"
    ['code/tests/Module2']="mod2"
)

declare -A team1_2rules=(
    ['code/uitests']="qa_ui"
    ['code/uitests/Module1']="mod1"
    ['code/uitests/Module2']="mod2"
)

declare -A team2_rules=(
    ['code']="dev"
    ['code/Module1']="mod1"
    ['code/Module2']="mod2"
)
```
2. Правим вызов метода `make_general_scope` в хуке `prepare-commit-msg`:
```bash
make_general_scope <do not touch other args> team1_rules team1_2rules team2_rules
```
Методу можно передать в качестве аргументов неограниченное число правил:

```bash
make_general_scope <do not touch other args> team1_rules team2_rules ... teamN_rules
```

#### Если в репозитории работает только одна команда
В таких случаях целесообразно в `scope` не указывать лейбл команды: это лишняя очевидная информация, поэтому в правилах значение нужно оставить пустым, а в ключе обозначить корневую директорию проекта точкой `'.'`:
```bash
declare -A team_rules=(
    ['.']=""
    ['Module1']="mod1"
    ['Module1/Submodule']="mod1-sub"
    ['Module2']="mod2"
)
```
В таком случае `scope` будет выглядеть компактнее `(mod1):` и при этом содержать подсказку, в каком логическом модуле произошли изменения.

- **ВАЖНО!** Правило для базовой директории (`'.'`) необходимо задавать и в случае, когда в репозитории работает только одна команда.

### Как мы заполняем информацию об идентификаторе задачи?
Хук вытаскивает ID задачи из имени ветки, в рамках которой работает инженер.
Пример ID задачи: `PROJ-123`, где `PROJ` — условный **ключ проекта**, `123` - порядковый номер задачи в рамках этого проекта.
Ключ для вашего проекта нужно задать в файле `githooks_config.sh` в переменной `jira_project_key`.

Если имя ветки содержит ID, удовлетворяющие регулярному выражению `PROJ[-_]*[0-9]+` (регистр игнорируется):
- my-branch-proj--123-implement-new-tests
- my_branch_proj_123_implement_new_tests
- MyBranchProj123ImplementNewTests

то в этом случае в конец сообщения будет добавлен `PROJ-123`. Если подходящий идентификатор в имени ветки не найден, то в сообщение он добавляться не будет.

### Как установить prepare-commit-msg хук?
Шаги установки рассчитаны на стандартную конфигурацию Git, в которой хуки хранятся в `.git/hooks/`. Если в репозитории настроена собственная директория хуков, используйте ее вместо `.git/hooks/`.

1. Откройте терминал или [git bash](https://git-scm.com/install/windows).
2. Перейдите в корень Git-репозитория, в который вы хотите добавить хук.
3. Загрузите хук, вспомогательные функции и конфиг из репозитория, выполнив следующие команды:
```bash
git clone --depth 1 https://gitverse.ru/PavelLiulchak/githooks.git /tmp/hooks
cp /tmp/hooks/prepare-commit-msg .git/hooks/
cp /tmp/hooks/hooks-helper-functions.sh .git/hooks/
cp /tmp/hooks/githooks_config.sh .git/hooks/
chmod +x .git/hooks/prepare-commit-msg
rm -rf /tmp/hooks
```
4. Откройте `githooks_config.sh`, задайте `jira_project_key` для вашего проекта, определите ассоциативные массивы с правилами именования `scope` для каждой команды.
